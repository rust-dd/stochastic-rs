Every stochastic source takes a [`SeedExt`](#seedext) strategy. A process takes it by value as the last constructor argument, `new(args…, seed)`; a distribution is a stateless law that binds to a seeded stream with `.seeded(&seed)` (see [Distributions](/docs/distributions#construction)).

## The two seed strategies

```rust
use stochastic_rs::simd_rng::Deterministic;
use stochastic_rs::simd_rng::Unseeded;
```

| Strategy                  | Behaviour                                       | When to use                              |
|---------------------------|-------------------------------------------------|------------------------------------------|
| **`Unseeded`**            | Auto-seeded from a globally unique sequence.    | Production sampling that need not be reproducible. |
| **`Deterministic::new(u64)`** | Reproducible stream rooted at the seed.     | Unit tests, regression baselines, calibration sweeps. |

## Auto-seeding and contention

`Unseeded` draws each RNG's seed from one global golden-ratio sequence (`base, base+γ, base+2γ, …`, each mixed through SplitMix64). Each thread reserves a **block** of $2^{18}$ consecutive steps from the global counter and walks it locally, so parallel construction touches the shared atomic once per $2^{18}$ seeds instead of once per seed. The blocks are disjoint and γ is odd, so every seed is still distinct. `Deterministic` never touches this counter.

## SeedExt

`SeedExt` lets a process or distribution accept either strategy:

```rust
pub trait SeedExt: Clone + Send + Sync + 'static {
  fn rng(&self) -> SimdRng; // single-stream RNG
  fn rng_ext<R: SimdRngExt>(&self) -> R; // generic backing RNG (see below)
  fn reseed(&self, seed: u64) {} // optional in-place reset
  fn next_seed(&self) -> u64; // fresh seed, advancing state like rng()/rng_ext()
}
```

`Unseeded` and `Deterministic` are the only implementations; the trait is sealed. A `Deterministic` clone is a snapshot of its state, not a shared handle.

## Reseeding in place

`SeedExt::reseed(seed)` resets a `Deterministic` source without rebuilding the process — for example a calibration loop that sweeps many seeds for one parameterised process:

<RustExample path="tests/doctest_concepts_seeding_reseed.rs" />

| Source           | `reseed(s)` behaviour                                         |
|------------------|---------------------------------------------------------------|
| `Unseeded`       | No-op (auto-seeded streams have nothing to reset).            |
| `Deterministic`  | The next stream advance starts from `s`.                      |

After `reseed(s)` the process draws bit-for-bit what `Deterministic::new(s)` would, which lets a calibration replay specific paths.

## Reproducibility invariants

1. **`Unseeded` × 2** — two instances produce different paths.
2. **`Deterministic(seed)` × 2** — bit-for-bit identical paths.
3. **Different seeds** — different paths.
4. **Same instance, repeated `sample()`** — each call advances the state, so successive paths differ.
5. **`reseed(s)` + sample** — reproduces what `Deterministic::new(s)` would produce.
6. **`Unseeded.reseed(s)`** — no-op, no panic, sampling still works.

Parallel sampling is bit-reproducible too: `sample_par` / `sample_map` return bit-identical output for the same seed and the same `m` under any Rayon thread-pool size. See [ProcessExt → parallel sampling and determinism](/docs/concepts/process-ext#parallel-sampling-and-determinism).

## SimdRngExt — generic backing RNG

`SimdRngExt` lets a seeded stream be generic over its backing SIMD RNG. The default is the single-stream [`SimdRng`](https://docs.rs/stochastic-rs-core/latest/stochastic_rs_core/simd_rng/struct.SimdRng.html); the experimental dual-stream [`SimdRngDual`](https://docs.rs/stochastic-rs-core/latest/stochastic_rs_core/simd_rng_dual/struct.SimdRngDual.html) comes with the [`unstable-dual-stream-rng`](#unstable-dual-stream-rng-feature) cargo feature.

```rust
pub trait SimdRngExt: rand::Rng + Clone + Debug + Sized + Send + Sync + 'static {
  const HAS_PAIR_ILP: bool = false;

  fn new() -> Self;
  fn from_seed(seed: u64) -> Self;
  fn next_i32x8(&mut self) -> wide::i32x8;
  fn next_i32x8_pair(&mut self) -> (wide::i32x8, wide::i32x8) {
    /* default = two single calls */
  }
  fn next_i32(&mut self) -> i32;
  fn next_f64(&mut self) -> f64;
  fn next_f32(&mut self) -> f32;
  fn fill_uniform_f64(&mut self, out: &mut [f64]);
  fn fill_uniform_f32(&mut self, out: &mut [f32]);
}
```

Through the `rand::Rng` supertrait, any `SimdRngExt` (including `SimdRng`) works wherever a `rand::Rng` is expected — e.g. `rand::distr::Distribution::sample`. The trait is sealed: `SimdRng` and `SimdRngDual` are its only implementations.

## `unstable-dual-stream-rng` feature

```toml
[dependencies]
stochastic-rs = { version = "3.0.0-rc.4", features = ["unstable-dual-stream-rng"] }
```

Unlocks `SimdRngDual`, the engine of a `Seeded::<SimdNormal<f64>, SimdRngDual>` or `Seeded::<SimdExp<f64>, SimdRngDual>` stream.

`SimdRngDual` carries two independent xoshiro engines. The ziggurat fill in `SimdNormal` / `SimdExp` draws one batch from each per iteration, and with no data dependency between them an out-of-order core overlaps the two batches' table lookups. On Apple Silicon that makes bulk Normal fills 2–6 % faster; Exp fills measure at parity and uniform fills gain nothing (numbers on [Benchmarks](/docs/benchmarks#dual-stream-rng)).

Trade-offs:

- **Deterministic streams differ.** `SimdRngDual::from_seed(s)` does not reproduce `SimdRng::from_seed(s)`'s output. The statistical properties are the same (KS-tested for Normal / Exp / LogNormal), but a test that pins specific numbers fails after switching.
- **Doubled RNG state**, roughly 768 bits per `SimdRngDual` against ~384 for `SimdRng`.
- **Architecture-dependent gain.** Measured on Apple Silicon; on CPUs with smaller reorder buffers the gain is likely smaller or zero.
- **Non-ziggurat distributions are unaffected.** Cauchy, Pareto, Beta, Gamma and NIG are bound by SIMD transcendentals (`ln`, `exp`, `cos`, `sin`, `powf`), not by the RNG.

The feature is off by default and outside the stability promise. Enable it only for ziggurat-dominated workloads (Normal, Exp, LogNormal) that can accept the changed streams.
