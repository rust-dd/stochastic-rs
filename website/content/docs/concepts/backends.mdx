# Sampling backends

The fractional / fGN process family selects **where** its FFT-based sampling
runs — CPU, CUDA, Metal, or Apple Accelerate — at **compile time**. A process is
parameterised by a backend marker `B` (defaulting to `Cpu`); the `Backend` trait
monomorphises `sample` / `sample_par` to that backend with **no runtime branch**.

This replaces the ad-hoc per-backend methods (`sample_cuda_native`,
`sample_gpu`, …) with one uniform selector. Those methods are now crate-private
(`sample_*_impl`, wired up in `stochastic_rs::stochastic::device`), so
`.on::<B>()` is not merely the recommended API — it is the only one.

## Switching backend

Re-type the process with the `.on::<B>()` turbofish, then sample as usual.
`CudaNative` only exists when the `cuda-native` feature is compiled (an
NVIDIA CUDA 12.x toolkit and GPU), which the CI runners that build this
site do not have, so this block is illustrative rather than compiled:

```rust
use stochastic_rs::simd_rng::Unseeded;
use stochastic_rs::stochastic::device::CudaNative;
use stochastic_rs::stochastic::noise::fgn::Fgn;
use stochastic_rs::traits::ProcessExt;

let cpu = Fgn::<f32, _>::new(0.7, 65_536, None, Unseeded).sample(); // default Cpu

let gpu = Fgn::<f32, _>::new(0.7, 65_536, None, Unseeded)
  .on::<CudaNative>()
  .sample(); // same call, runs on the GPU
```

`.on::<B>()` consumes the process and returns it re-typed to backend `B` — the
fields are moved, nothing is copied, and the choice is resolved at compile time.

## The `Backend` marker and the `FgnBackend` capability

`Backend` itself is a bare device marker — it carries no algorithm. What a
device can compute is expressed by capability subtraits, and **every process
carries the backend as its last type parameter** (`Name<T, S, B = Cpu>`), so
`.on::<B2>()` exists on all of them; the capability the process's bound names
says which markers it accepts:

- `HostBackend: Backend` — the process samples on the CPU through its own
  `ProcessExt` sampler. `Cpu` and `Accelerate` implement it. Every process
  accepts at least these; a process whose only bound is `HostBackend` has no
  device kernel yet, and gaining one later merely widens the bound, which
  breaks no caller.
- `FgnBackend: Backend` — fractional Gaussian noise on the device (FFT
  pipeline); the fGN-driven family (`Fgn`, `Fbm`, `Fou`, `Fcir`, `Fgbm`,
  `FJacobi`, `Cfou`, `Cfgns`, `JumpFou`, `JumpFOUCustom`, `Sde`) is bound on it.
- `EulerBackend: Backend` — the Euler engine's device kernels (`Gbm`, `Ou`,
  `Cir` today); `Cpu` and `Accelerate` implement it as the host sampler.

Bound on `Backend` to say "device-parameterised"; bound on a capability when
the code actually samples through it.

| Marker        | Feature                          | Backs onto                             | Hardware            |
|---------------|----------------------------------|----------------------------------------|---------------------|
| `Cpu`         | — (always available, default)    | `ndrustfft` + CPU SIMD, rayon batches  | any CPU             |
| `CudaNative`  | `cuda-native`                    | `cudarc` + cuFFT, JIT Philox RNG       | NVIDIA, CUDA 12.x   |
| `CubeCl`      | `gpu` / `gpu-cuda` / `gpu-wgpu`  | `cubecl` portable kernels              | NVIDIA / AMD / wgpu |
| `MetalNative` | `metal`                          | hand-written MSL via the `metal` crate | Apple GPU (f32)     |
| `Accelerate`  | `accelerate`                     | Apple vDSP FFT (CPU), rayon batches    | macOS               |

`Backend`, `Cpu` and `FgnBackend` are re-exported at
`stochastic_rs::traits`; the GPU markers
live under `stochastic_rs::stochastic::device` and **only exist when their
feature is compiled**. Selecting an unavailable backend is therefore a *compile
error*, not a silent runtime fallback.

## Which processes support it

The per-family inventory — which process runs on which device, at what
precision, and what the Python entry point is — lives on
[GPU support](/docs/concepts/gpu-support); this section explains the
mechanism.

All 131 processes carry the parameter and accept `.on::<Cpu>()` (and
`.on::<Accelerate>()` under the `accelerate` feature). Device kernels exist for
two families today: the fGN-driven processes (`FgnBackend`: `Fgn`, `Fbm`,
`Fou`, `Fcir`, `Fgbm`, `FJacobi`, `Cfou`, `Cfgns`, `JumpFou`, `JumpFOUCustom`,
`Sde`), whose hot path is a circulant-embedding FFT, and the Euler engine's
scalar diffusions (`EulerBackend`: `Gbm`, `Ou`, `Cir`), which run the whole
Euler–Maruyama recursion in one kernel launch. Every other process is bound on
`HostBackend`: selecting a GPU marker for it is a compile error, and adding a
kernel later widens the bound without touching callers.

## Precision

Apple GPUs have no `f64`, so `MetalNative` is **`f32` only**. `CudaNative`,
`CubeCl`, and `Accelerate` support both `f32` and `f64`; the `Cpu` backend
follows the process's `T` parameter.

## When is GPU worth it?

The discrete-GPU win is real but narrow — it shows up for large `n` (≥ 16 k) and
batched sampling, while for small `n` the CPU SIMD path wins on launch latency.
See the [Benchmarks](/docs/benchmarks) page for the cross-over numbers, and the
[Feature flags](/docs/concepts/feature-flags) page for how to enable each
backend.
