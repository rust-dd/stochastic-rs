Every process chooses **where** it samples — CPU, CUDA, Metal or Apple Accelerate — through a backend type parameter `B` (default `Cpu`), fixed at compile time.

## Switching backend

Re-type the process by naming a backend marker, then sample as usual. `Cuda` only exists when the `cuda` feature is compiled:

```rust
use stochastic_rs::simd_rng::Unseeded;
use stochastic_rs::stochastic::device::Cuda;
use stochastic_rs::stochastic::noise::fgn::Fgn;
use stochastic_rs::traits::ProcessExt;

let cpu = Fgn::<f32, _>::new(0.7, 65_536, None, Unseeded).sample(); // default Cpu

let gpu = Fgn::<f32, _>::new(0.7, 65_536, None, Unseeded)
  .on::<Cuda>()
  .sample(); // same call, runs on the GPU
```

`.on::<B>()` consumes the process and returns it re-typed to backend `B`; the fields are moved, not copied.

## The `Backend` trait

`Backend` is a bare device marker; it carries no algorithm. What a device can compute is expressed by capability subtraits. **Every process carries the backend as its last type parameter** (`Name<T, S, B = Cpu>`), so `.on::<B>()` exists on all of them, and the capability the process's bound names decides which markers it accepts:

- `HostBackend: Backend` — the process samples on the CPU through its own sampler. `Cpu` and `Accelerate` implement it.
- `FgnBackend<T>: Backend` — fractional Gaussian noise on the device (the circulant-embedding FFT pipeline); `Fgn` is bound on it, and the fractional processes take their increments from it.
- `SheetBackend<T>: Backend` — the two-dimensional circulant embedding behind the fractional Brownian sheet `Fbs`.
- `EulerBackend<T>: Backend` — the Euler engine's device kernels, which 130 processes step through; `Cpu` and `Accelerate` implement it as the host sampler.

The three device capabilities take the scalar, and a device implements them only for the precision its kernels compute in: `Cuda` for `f32` and `f64`, `Metal` for `f32`, the CPU devices for both. `Fgn<f64>` or `Gbm<f64>` on `Metal` is a compile error; nothing runs in `f32` behind an `f64` type. Generic code spells the scalar in the bound: `B: EulerBackend<T>`.

Bound on `Backend` to say "device-parameterised"; bound on a capability when the code actually samples through it. The family is sealed to the four handles below.

| Marker        | Feature                          | Backs onto                             | Hardware            |
|---------------|----------------------------------|----------------------------------------|---------------------|
| `Cpu`         | — (always available, default)    | `ndrustfft` + CPU SIMD, rayon batches  | any CPU             |
| `Cuda`        | `cuda`                           | `cudarc` + cuFFT, NVRTC kernels        | NVIDIA GPU          |
| `Metal`       | `metal`                          | MSL kernels via the `metal` crate      | Apple GPU (`f32`)   |
| `Accelerate`  | `accelerate`                     | Apple vDSP FFT (CPU), rayon batches    | macOS               |

`Backend`, `Cpu`, `HostBackend`, `FgnBackend`, `SheetBackend` and `EulerBackend` are re-exported at `stochastic_rs::traits`; the device markers live under `stochastic_rs::stochastic::device` and **only exist when their feature is compiled**, so selecting an unavailable backend is a compile error.

## Which processes support it

All 132 processes carry the parameter and reach a device: 130 through the Euler engine (`EulerBackend`), `Fgn` through its FFT pipeline (`FgnBackend`) and `Fbs` through the sheet pipeline (`SheetBackend`). The per-family inventory — which process runs on which device, at what precision, and its Python entry point — is on [GPU support](/docs/concepts/gpu-support).

## One fallback rule

Some configurations exceed what the kernels carry: a grid past a per-path array, a dimension past the four state slots, a coefficient written as a closure, a point process in horizon mode. Every process answers `device_ready()` — a `ProcessExt` method, `true` by default — for the configuration it holds, and a `false` never fails: on any backend the process then samples on the host through its own sampler, bit-identically to the `Cpu` build. `try_sample` is `Ok` on that path, and `sample` never panics for a configuration — only a device that fails to open, compile or launch does. So `gbm.on::<Cuda>()` always runs on the GPU, while `wishart.on::<Cuda>()` runs there for `d = 2` and on the host for `d = 3`.

`device_fallback()` returns the reason — `Some("a Wishart outside the two-dimensional cone the kernel steps")` — and `None` when a kernel carries the configuration; `device_ready()` is the absence of a reason. Check it, because the fallback is otherwise silent and costs an order of magnitude in speed:

```rust
if let Some(why) = wishart.device_fallback() {
  eprintln!("sampling on the host: {why}");
}
```

Both are `ProcessExt` methods, and both are available from Python as `process.device_fallback()` and `process.device_ready()`.

`process.backend()` returns the handle the process holds (ordinal and batch budget), and `process.probe()` opens the device behind it and describes it, or reports why it cannot be used.

## Choosing the device

A backend is a value, not only a type. `.on::<B>()` re-types the process with `B`'s default handle; `with_backend(handle)` takes an explicit one:

```rust
use stochastic_rs::stochastic::device::Cuda;

let on_second_gpu = gbm.with_backend(Cuda::new(1).with_batch_budget(256 << 20));
```

`Cuda` and `Metal` carry the device ordinal (the CUDA ordinal; the index into `Device::all()` on Metal) and the bytes of path data one launch may hold, readable as fields and built with `Cuda::new(1)`, `.with_batch_budget(..)` or `Cuda::default()` (ordinal `0`, 1 GiB); the structs are `#[non_exhaustive]`, so a struct literal does not compile. `Cuda::from_env()` reads `STOCHASTIC_RS_DEVICE` and `STOCHASTIC_RS_DEVICE_BATCH_BYTES` and returns `Err(DeviceError::Config)` for a value it cannot use. There is no process-wide device state: two processes on two GPUs hold two handles. `Cpu` and `Accelerate` carry nothing.

## Probing a device and handling its failures

A missing GPU, a runtime that will not start or a kernel that will not compile is an environmental failure, reported as a value:

```rust
use stochastic_rs::stochastic::device::{Backend, DeviceError, Metal};

match Metal::default().probe() {
  Ok(info) => println!("{} on {} ({:?})", info.backend, info.name, info.precisions),
  Err(DeviceError::Unavailable(why)) => eprintln!("no device: {why}"),
  Err(other) => eprintln!("{other}"),
}
```

`probe()` opens the device behind the handle and describes it (`backend`, `name`, `precisions`, `ordinal`). The plain `sample()` / `sample_par(m)` calls panic with the device's error if something still fails at launch time (an allocation, typically); `try_sample()` / `try_sample_par(m)` return `Result<_, DeviceError>` instead (always `Ok` on the host devices, bit-identical to the plain calls). `DeviceError` is `#[non_exhaustive]` with `Unavailable`, `Compile`, `Launch`, `OutOfMemory` and `Config`. From Python, a device failure is a `RuntimeError` with the same message.

## Precision

Apple GPUs have no `f64`, so `Metal` is **`f32` only**: an `f64` process on it is a compile error. `Cuda`, `Accelerate` and `Cpu` follow the process's `T` in `f32` and `f64`.

## When is GPU worth it?

A device pays off for large batches and long grids; for small batches and short single paths the CPU SIMD path wins on launch latency. The cross-over numbers are on [Benchmarks](/docs/benchmarks), and [Feature flags](/docs/concepts/feature-flags) shows how to enable each backend.
