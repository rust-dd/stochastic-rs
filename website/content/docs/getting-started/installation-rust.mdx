The Rust crates require Rust 1.89 or newer; on Apple Silicon the `ai` feature needs Rust 1.94 or newer (see the [feature flags](/docs/concepts/feature-flags#common-gotchas)).

```toml

stochastic-rs = "3.0.0-rc.4"
```

## Per-sub-crate (lean)

For less compile time and fewer dependencies, depend only on the sub-crates you need:

```toml
[dependencies]
stochastic-rs-distributions = "3.0.0-rc.4"   # SIMD distribution sampling
stochastic-rs-stochastic = "3.0.0-rc.4"   # 132 process types
stochastic-rs-copulas = "3.0.0-rc.4"   # bivariate / multivariate copulas
stochastic-rs-stats = "3.0.0-rc.4"   # estimators
stochastic-rs-quant = "3.0.0-rc.4"   # pricing / calibration / vol surface
stochastic-rs-ai = "3.0.0-rc.4"   # experimental neural surrogates (candle)
```

Topology:

```
stochastic-rs-core (simd_rng)
 └→ stochastic-rs-distributions (FloatExt, SimdFloatExt, distributions)
     ├→ stochastic-rs-stochastic (ProcessExt + 132 processes)
     ├→ stochastic-rs-copulas
     └→ stochastic-rs-stats
         └→ stochastic-rs-quant (ModelPricer, calibration, vol surface)
             └→ stochastic-rs-ai
```

## Cargo features

The default build links no GPU, no BLAS and no Python. The optional features are `cuda`, `metal` and `accelerate` (device back-ends), `ai` and `ai-metal` (neural surrogates), `viz` (HTML plots) and `unstable-dual-stream-rng`; the [feature flags](/docs/concepts/feature-flags) page lists what each pulls in.

## Public dependencies

The umbrella re-exports `ndarray`, `num_complex`, `num_traits`, `rand` and `chrono` (as `stochastic_rs::ndarray` and so on) because callers build and pass their types; use these paths or depend on the same versions. `wide` (the SIMD vectors of `SimdFloatExt` and `SimdRngExt`) and `anyhow` (calibration and SLV errors) also appear in public signatures. A semver-incompatible release of any of these seven crates (for a 0.x crate, a minor bump such as ndarray 0.17 → 0.18) is a major release of `stochastic-rs`.

## SIMD support

Numerical hot paths (FGN Davies-Harte, all `Simd*` distributions, `fill_slice` on a seeded stream, `fill_with` from any rng) use the [`wide`](https://crates.io/crates/wide) crate for portable SIMD, with **8-lane** types throughout:

- `f32x8` — 8 × `f32` = 256 bits
- `f64x8` — 8 × `f64` = 512 bits
- `i32x8` — for the integer Box-Muller / ziggurat tables

`wide` picks the instructions at **build time** from the enabled target features. Where the target has no register of the full width, it splits the vector into halves of the widest one it has:

| Target                     | Default ISA | What `wide` emits without extra flags                  |
|----------------------------|-------------|--------------------------------------------------------|
| `x86_64-…` (Linux, MSVC)   | SSE2        | 128-bit SSE2: `f32x8` as two halves, `f64x8` as four   |
| `x86_64-…` with `+avx2`    | AVX2        | Full 256-bit SIMD on `f32x8`                           |
| `x86_64-…` with `+avx512f` | AVX-512     | Full 512-bit SIMD on `f64x8`                           |
| `aarch64-apple-darwin`     | NEON        | 128-bit NEON, two halves for `f32x8`                   |

## Native CPU optimization

Default builds target the plain `x86-64` / `aarch64` baseline so the binary or wheel runs on any CPU of the same architecture. For SIMD-heavy paths (`fill_slice` on a seeded `SimdNormal` stream, `Fgn` Davies-Harte, `sample_par`, …) a higher baseline pays off:

```bash
# Local dev / benchmarks: every feature the build host supports.
# The resulting binary only runs on this exact CPU family.
RUSTFLAGS="-C target-cpu=native" cargo build --release
RUSTFLAGS="-C target-cpu=native" cargo bench

# Higher x86-64 baselines (binary runs on any CPU meeting the level):
#   v2 — SSE4.2 + POPCNT     (x86_64 CPUs since ~2009)
#   v3 — AVX2 + BMI2 + FMA   (x86_64 CPUs since ~2013–2015)
#   v4 — AVX-512             (most server CPUs only; absent from all
#                             AMD Zen 1–3 and Intel client 12th-gen+)
RUSTFLAGS="-C target-cpu=x86-64-v3" cargo build --release
```

<Callout type="warn">
**Public distribution (PyPI wheels, openly shared Docker images): keep the default `x86-64` baseline.** `pip` wheel tags don't dispatch by CPU feature level, so a `v3` wheel will `SIGILL` on pre-2013 hardware (AMD Bulldozer/Piledriver, Sandy/Ivy Bridge, Atom variants). Use `v2`/`v3`/`v4` only where every target host clears the level (an internal Docker fleet, a homogeneous HPC cluster, a CI runner pinned to a known SKU), and `target-cpu=native` only for local dev and benchmarks.
</Callout>

## GPU support

Every process can sample on a device backend: `cuda` (NVIDIA), `metal` (Apple GPUs) and `accelerate` (Apple vDSP on the CPU). See [GPU support](/docs/concepts/gpu-support) for what runs where.

### The `.on::<B>()` selector

Select a backend with `.on::<B>()`, then call `sample()` / `sample_par()` as usual:

```rust
use stochastic_rs::simd_rng::Unseeded;
use stochastic_rs::stochastic::device::Cuda;
use stochastic_rs::stochastic::noise::fgn::Fgn;
use stochastic_rs::traits::ProcessExt;

let path = Fgn::<f32, _>::new(0.7, 65_536, None, Unseeded)
  .on::<Cuda>() // Cuda | Metal | Accelerate | Cpu
  .sample();
```

The markers only exist when their feature is compiled, so an unavailable backend is a compile error. `with_backend(handle)` takes an explicit handle (a second GPU, a batch budget); see [Backends](/docs/concepts/backends).

### `cuda` — NVIDIA

[`cudarc`](https://crates.io/crates/cudarc) + cuFFT + NVRTC. **No `.cu` files, no `nvcc` step**: the kernels ship as source strings and are compiled at run time by NVRTC. Requires the NVIDIA CUDA toolkit on the build machine and a compatible GPU.

```bash
cargo build --features cuda
cargo bench --features cuda --bench fgn_cuda
```

```rust
use stochastic_rs::simd_rng::Unseeded;
use stochastic_rs::stochastic::device::Cuda;
use stochastic_rs::stochastic::noise::fgn::Fgn;
use stochastic_rs::traits::ProcessExt;

let path = Fgn::<f32, _>::new(0.7, 65_536, None, Unseeded)
  .on::<Cuda>()
  .sample(); // single path on GPU
let batch = Fgn::<f32, _>::new(0.7, 65_536, None, Unseeded)
  .on::<Cuda>()
  .sample_par(1024); // 1024 paths in one launch
```

### `metal` — Apple GPUs (macOS)

The [`metal`](https://crates.io/crates/metal) crate, on Apple Silicon and Intel Macs. Apple GPUs have no `f64`, so the `Metal` backend is `f32` only.

```bash
cargo build --features metal
cargo bench --features metal --bench fgn_metal
```

```rust
use stochastic_rs::stochastic::device::Metal;

let path = Fgn::<f32, _>::new(0.7, 65_536, None, Unseeded)
  .on::<Metal>()
  .sample();
```

### `accelerate` — Apple Accelerate (macOS, no GPU)

Routes the fGN FFT through Apple's vDSP (part of macOS, no extra install); a process that draws no fGN samples exactly as on `Cpu`. Lower latency than the GPU paths for medium-`n` workloads where launch overhead dominates.

```bash
cargo build --features accelerate
cargo bench --features accelerate --bench fgn_accelerate
```

```rust
use stochastic_rs::stochastic::device::Accelerate;

let path = Fgn::<f32, _>::new(0.7, 65_536, None, Unseeded)
  .on::<Accelerate>()
  .sample();
```

The cross-over points between the CPU and each backend are on the [Benchmarks](/docs/benchmarks) page.

## Linear algebra

Cholesky, SVD, eigendecompositions and least squares run on the pure-Rust [`faer`](https://github.com/sarah-quinones/faer-rs) and are always compiled in; there is no BLAS/LAPACK system dependency on any platform.
