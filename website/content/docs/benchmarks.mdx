## FGN — CPU vs CUDA

`cuda` backend: cudarc + cuFFT + a fused Philox RNG kernel. Environment: Intel i9-285K + NVIDIA RTX 4070 SUPER, CUDA 12.x, Rust nightly, `--release` with LTO.

```bash
cargo bench --features cuda --bench fgn_cuda
```

### Single path (`f32`, H = 0.7)

| n      | CPU `sample` | `.on::<Cuda>().sample()` | Speedup    |
|-------:|-------------:|-------------------------:|-----------:|
|  1,024 |       8.1 µs |                    46 µs |      0.18× |
|  4,096 |        35 µs |                    84 µs |      0.42× |
| 16,384 |       147 µs |                   110 µs |   **1.3×** |
| 65,536 |       850 µs |                   227 µs |   **3.7×** |

### Batch (`sample_par(m)`, `f32`, H = 0.7)

| n, m         | CPU `sample_par` | Cuda `sample_par` | Speedup   |
|--------------|-----------------:|------------------:|----------:|
|   4,096, 32  |          147 µs  |            117 µs |  **1.3×** |
|   4,096, 512 |         1.78 ms  |           2.37 ms |    0.75×  |
|  65,536, 128 |         12.6 ms  |           10.5 ms |  **1.2×** |
|  65,536, 1 k |          102 ms  |             93 ms |  **1.1×** |

CUDA wins for large `n` (≥ 16 k) single paths and stays competitive on `n = 65 k` batches; for medium `n` the CPU's rayon parallelism wins on zero transfer overhead.

## All backends head-to-head

`fgn_all_backends` (requires `metal` and `accelerate`) compares the CPU, Metal and Accelerate on the same fGN sampler over `n ∈ {1024, 4096, 16384, 65536}` single paths and `(n, m) ∈ {(4 096, 32), (4 096, 128), (4 096, 512), …}` batches. Run it to find the cross-over points on your own machine. The Metal fGN pipeline's current numbers are in [The fGN pipeline on Metal](#the-fgn-pipeline-on-metal).

### Single path (`f32`, H = 0.7)

**Apple M4 Max** (10 P + 4 E cores, 36 GB unified; measured 2026-09-03):

| n      | CPU       | Accelerate |
|-------:|----------:|-----------:|
|  1,024 | **12 µs** |    12 µs   |
|  4,096 |    53 µs  |  **48 µs** |
| 16,384 |   219 µs  | **180 µs** |
| 65,536 |   901 µs  | **750 µs** |

**Intel i9-285K + RTX 4070 SUPER** (`cudarc` + cuFFT; converted from the `Melem/s` values in [`CUDA_BENCHMARK.md`](https://github.com/rust-dd/stochastic-rs/blob/main/CUDA_BENCHMARK.md), `fgn_cuda_compare`):

| n      | CPU (i9-285K) | cuFFT (`cuda`) |
|-------:|--------------:|---------------:|
|  1,024 |    **7.9 µs** |          80 µs |
|  4,096 |     **34 µs** |          84 µs |
| 16,384 |        144 µs |     **110 µs** |
| 65,536 |        847 µs |     **189 µs** |

The SIMD CPUs dominate short paths (the i9-285K is the fastest of all up to `n = 4 k`); **cuFFT overtakes at `n ≈ 16 k`** and reaches **4.4× over the CPU at `n = 65 k`**. On the Apple side the vDSP (Accelerate) FFT edges the `ndrustfft` CPU from `n = 4 k`.

### Batch throughput (`sample_par`, `f32`, H = 0.7) — Melem/s, higher is better

**Apple M4 Max** (measured 2026-09-03):

| n × m           |     CPU | Accelerate |
|-----------------|--------:|-----------:|
| 4,096 × 32      |     414 |    **446** |
| 4,096 × 128     |     585 |    **628** |
| 4,096 × 512     |     597 |        597 |
| 16,384 × 128    | **596** |        577 |
| 16,384 × 512    | **602** |        535 |
| 1,024 × 1,024   |     532 |    **572** |
| 4,096 × 16,384  | **591** |        585 |
| 16,384 × 16,384 | **568** |        526 |
| 65,536 × 16,384 | **530** |        464 |

**Intel i9-285K + RTX 4070 SUPER** — small `n` stays cache-resident on the 24-core i9; batched cuFFT wins once `n ≥ 4 k`:

| n × m           | CPU (i9-285K) |   cuFFT |
|-----------------|--------------:|--------:|
| 1,024 × 16,384  |      **1751** |     557 |
| 4,096 × 16,384  |           269 | **581** |
| 4,096 × 65,536  |           118 | **383** |
| 16,384 × 16,384 |            59 | **183** |
| 65,536 × 4,096  |       **504** |     236 |

**Takeaway:** for fGN a discrete NVIDIA GPU wins from `n ≥ 16 k` single paths and `n ≥ 4 k × m ≥ 16 k` batches. On Apple Silicon the CPU-side FFTs (`ndrustfft` + rayon, vDSP/Accelerate) hold 530–630 Melem/s on batches, and Metal batches are faster still (next sections). A Colab T4 run of the CUDA path is on the [GPU support](/docs/concepts/gpu-support) page.

## Euler engine — CPU against Metal

The recursion, not the FFT: one thread per path, the whole step loop in the kernel. Steps per second (paths × grid points ÷ wall time), GBM in `f32`, best of nine runs through `sample_map_view`, **Apple M4 Max** (14 CPU cores, 40 GPU cores), measured 2026-09-07.

| paths | steps | CPU | Metal | Metal / CPU |
|------:|------:|----:|------:|------------:|
| 1 000 | 1 024 | 1.63 G | 0.82 G | 0.5× |
| 10 000 | 1 024 | 2.48 G | **6.97 G** | 2.8× |
| 50 000 | 1 024 | 2.77 G | **17.40 G** | 6.3× |
| 200 000 | 1 024 | 2.72 G | **45.79 G** | 16.8× |
| 100 000 | 4 096 | 2.73 G | **47.67 G** | 17.5× |

A thousand paths is still the CPU's: one launch has a fixed cost, and at a million steps there is nothing to amortise it over. From ten thousand paths the device leads, and the lead widens with the batch. Storing every step in `f32` caps this kernel at about 68 G steps/s on this machine — the memory system's write ceiling; the kernel alone runs at 50–52 G.

### The fGN pipeline on Metal

fGN batches on the M4 Max's GPU:

| paths | points | time |
|------:|-------:|-----:|
| 1 000 | 4 096 | 2.24 ms |
| 1 000 | 16 384 | 3.28 ms |
| 10 000 | 4 096 | 4.63 ms |

That is 8.85 G points/s at 10 000 × 4 096. The thousand-path shapes are noise-dominated: four million points is too little for the device work to set the wall time.

### `sample_map_view` against `sample_map`

`sample_map` hands the callback an owned path, so a device batch — one `m × n` block — is copied row by row after it lands. `sample_map_view` hands the callback an `ArrayView1` of the block instead, so the batch is traversed once; most callbacks compile unchanged, since a view indexes, iterates and reduces like the array it borrows. On Metal that is 1.4–2.1× faster for GBM batches of 10 000–200 000 paths × 1 024 steps. On the host the two are within noise of each other: a host path is already an owned array.

## Euler engine — CPU against CUDA

The same measurement (`examples/cuda_engine_profile`) on a **Tesla T4** in a Colab runtime, best of five, measured 2026-09-07. The host there is a small shared VM whose CPU column runs at about a tenth of the M4 Max's, so read the ratio, not the absolute.

| paths | steps | dtype | CPU | CUDA | CUDA / CPU |
|------:|------:|:------|-------:|-------:|-----------:|
| 10 000 | 1 024 | `f32` | 0.21 G | **2.35 G** | 10.96× |
| 50 000 | 1 024 | `f32` | 0.21 G | **1.58 G** | 7.41× |
| 10 000 | 4 096 | `f32` | 0.21 G | **2.49 G** | 11.77× |
| 10 000 | 1 024 | `f64` | 0.21 G | **0.66 G** | 3.19× |
| 50 000 | 1 024 | `f64` | 0.20 G | **0.65 G** | 3.25× |
| 10 000 | 4 096 | `f64` | 0.21 G | **0.81 G** | 3.83× |

The bus binds here, not the kernel: 10 000 paths over 1 024 steps in `f32` is 41 MB, and 4.4 ms of it is 9.3 GB/s — PCIe 3.0 ×16 with page-locked memory, near its practical ceiling. Every step's four bytes have to cross, so this shape cannot pass about 3 G steps/s on this card, and 2.35–2.49 is 78–83 % of that. To go further, reduce on the device and return the reduction. `f64` sits at about a third of `f32`, where the T4's 1/32 double-precision rate shows. The M4 Max reaches 45.8 G steps/s on the same kernel mostly because its unified memory needs no copy at all.

The fractional pipeline on the T4 is FFT-bound, so far more device work rides on each byte copied back:

| paths | points | CPU | cuFFT | cuFFT / CPU |
|------:|-------:|--------:|---------:|------------:|
| 1 000 | 4 096 | 81.7 ms | **20.7 ms** | 3.94× |
| 1 000 | 16 384 | 354.5 ms | **121.0 ms** | 2.93× |
| 10 000 | 4 096 | 837.1 ms | **300.4 ms** | 2.79× |

## Normal sampling vs `rand_distr` (single-thread, `fill_slice`)

Measured with `cargo bench --bench dist_multicore`, single-thread `fill_slice`, median of 7 runs. Three implementations of the same workload (write `n` `N(0, 1)` samples into a pre-allocated `Vec<f64>`):

- **`SimdNormal::fill_slice`** — the SIMD ziggurat with the `wide`-based RNG.
- **`rand_distr + SimdRng`** — `rand_distr::Normal::sample` consuming `SimdRng`. Isolates the Normal algorithm: both share the same uniform stream.
- **`rand_distr + rand::rng()`** — `rand_distr::Normal` on `rand::rng()` (`ThreadRng`-backed ChaCha).

|      n  | `SimdNormal` (µs) | `rand_distr + SimdRng` (µs) | speedup | `rand_distr + rand::rng()` (µs) | speedup |
|--------:|------------------:|-----------------------------:|--------:|---------------------------------:|--------:|
|       4 |             0.008 |                        0.013 |  1.73×  |                            0.032 |  4.22×  |
|       8 |             0.014 |                        0.026 |  1.78×  |                            0.065 |  4.52×  |
|      16 |             0.029 |                        0.051 |  1.79×  |                            0.128 |  4.47×  |
|      64 |             0.109 |                        0.208 |  1.90×  |                            0.508 |  4.64×  |
|     256 |             0.432 |                        0.840 |  1.94×  |                            2.029 |  4.70×  |
|   4 096 |             6.975 |                       13.176 |  1.89×  |                           32.382 |  4.64×  |
|  65 536 |           113.458 |                      212.406 |  1.87×  |                          520.219 |  4.59×  |

The `rand_distr + SimdRng` column is the algorithmic gain of the SIMD ziggurat over the scalar reference (~1.7–1.9×); the `rand_distr + rand::rng()` column adds the SIMD RNG (~4.2–4.7×).

## Dual-stream RNG

The `unstable-dual-stream-rng` feature's `SimdRngDual` against the single-stream `SimdRng` for `SimdNormal` fills on Apple Silicon, measured 2026-06-11 (`cargo bench --bench dual_stream_compare --features unstable-dual-stream-rng`):

|         n | single (`SimdRng`) | dual (`SimdRngDual`) |    Δ   |
|----------:|-------------------:|---------------------:|-------:|
|        64 |              120.6 ns |                117.5 ns |  −2.6% |
|       256 |              494.2 ns |                467.9 ns |  −5.3% |
|     4 096 |               7.87 µs |                 7.42 µs |  −5.7% |
|    65 536 |              126.2 µs |                122.4 µs |  −3.0% |
| 1 048 576 |               2.02 ms |                 1.97 ms |  −2.2% |

Exponential fills measure at parity, and uniform `f64` fills show no speedup beyond noise. The trade-offs are on the [seeding page](/docs/concepts/seeding#unstable-dual-stream-rng-feature).

## Running the benchmarks

```bash
# Save the current build as a baseline, then compare a later build against it
cargo bench --bench distributions -- --save-baseline before
cargo bench --bench distributions -- --baseline before
```

`criterion` reports `Performance has improved` / `regressed` per benchmark with the effect size and a 95 % confidence interval.

To reproduce the FGN-vs-CUDA tables you need an NVIDIA GPU with the CUDA toolkit, and `RUSTFLAGS="-C target-cpu=native"` for the CPU side — without it `wide` emits 128-bit SSE2 instead of AVX2 / AVX-512 on x86-64 and the CPU column comes out slower (see [Native CPU optimization](/docs/getting-started/installation-rust#native-cpu-optimization)):

```bash
RUSTFLAGS="-C target-cpu=native" cargo bench \
  --features cuda \
  --bench fgn_cuda -- --save-baseline local
```
